# 性能台账复检（perf ledger pass）

对 `docs/known-issues.md` §一（性能问题）与 `docs/backlog.md` 开放项做一轮「复核暂缓理由 → 挑可做的实施 → 台账回写」的迭代。台账是**决策记录**，不是待办堆：每一条「暂缓」都有当时的理由，复检的价值在于用新代码现实重新审判这些理由。

## 何时跑

- 用户要求性能优化 / 自由发挥改进时；
- 一批功能合并后（新代码会改变旧瓶颈的成本结构与风险假设）；
- 台账顶部批注行长期未动、或累计了新登记项时。

## 流程

1. **盘点**：读 known-issues §一 表格所有 ☐/部分修 项 + backlog 开放项，忽略已 ☑ 项。
2. **逐项复核暂缓理由**（§一.F 明细），每项问三个问题：
   - 该路径是低频还是高频？（低频交互路径的收益通常仍不抵扰动）
   - 改动面是否真的大于收益？（需要新增批量 API、动正确性路径的，谨慎降级）
   - 当时的风险假设有没有被新代码推翻？（如新加的缓存/功能改变了某路径的频次或语义）
3. **挑 2–4 项实施**（单分支多个逻辑提交、按文件面分区；每项独立 commit，改法先用一句话说清）：
   - 行为语义必须透明：缓存 / 并行化 / 预计算 / 条件跳过，不改变对外语义。
   - **涉及共享可变状态（Config、缓存对象）的一律走「memo 存原始对象 + 每次调用返回 structuredClone」范式**（AGENTS.md「缓存 Config/可变对象时绝不外借共享实例」），并且**必须跑 `test/synctarget.test.ts` 端到端**——新单测全绿 ≠ 安全（2026-10-29 loadConfig memo 教训：单测绿、端到端红，还由此揪出 CORRECT-06 既有竞态）。
   - 同步域改动动手前先读 §三 的 CORRECT 项（CORRECT-06 的 config 锁原子化语义）。
4. **验证**：`npm test` 全量绿。`isolate:false` 单进程串行（见 AGENTS.md「vitest 隔离模型」），**必须全量跑**，新文件单独跑绿不算数。
5. **台账回写**（同分支提交）：表格行状态（☑/部分修 + `@<commit hash>`）→ §一.F 明细批注（保留原暂缓理由，追加新批注——不要删历史）→ 顶部批注行。**维持暂缓的项写明「复核后维持」与理由**；顺带发现的新问题当场登记新条目（如 CORRECT-06）。
6. 文档与代码走 feature-branch 工作流分支，finish 自动验证。

## 已知坑（2026-10-29 批实证）

- **memo 外借共享 Config 对象 = 端到端竞态**：`mutateConfig` 的 fn 原地改它拿到的对象；外借共享实例会让「未落盘的中间状态」立刻被其他调用者看见，把并发写确定性钉进 apply→post-collect 窗口（见 CORRECT-06）。clone 成本远低于重新 parse，永远 clone。
- **collectSyncdoc 整包记忆是语义陷阱**：keychain 后端 set-key 只写钥匙串、不落任何被同步文件的盘，整包 mtime 短路会把旧明文 key 继续推给其他机器——密钥解析保持每次现取（其自身 TTL 缓存已吸收 spawn 成本）。
- **新配置键必过三道门**：types + store.migrate 登记（loadConfig 按白名单重建，漏登记 = 落盘后静默丢失）/ `gen-config-reference.mjs` METAS+SECTIONS / syncdoc 三处——见 AGENTS.md「新增 config.toml 键有三道同步义务」。
- **并行会话的 finish 检出冲突**：处置经验见 `feature-branch.md` §4「并行会话的检出冲突」。
- **度量先行**：有怀疑先 grep/读代码确认（如热路径同步 I/O 审计：`grep -n "readFileSync\|statSync\|existsSync" src/gateway/`），没有实测依据的微优化不做——本仓库历次性能批次的经验是「审计发现多数路径已被此前的批次优化干净」，避免为改而改。
