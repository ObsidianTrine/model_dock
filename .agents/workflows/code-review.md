# code-review（合并前独立审查工作流）

`feature-branch.mjs finish` 只跑 `npm test`——它验证"测试通过"，但不验证"改动本身合理"。本工作流补上这一环：**合并前用一个全新上下文的审查者看 diff**。

> **何时用**：任何 `finish` 之前（非 `--skip-test` 的代码改动必做；纯文档改动建议做）。
> **核心原理**：审查者在全新上下文里只看 diff 和验收标准，看不到实现过程中的中间推理——这让它能发现实现者"想当然"跳过的问题。

## 流程

### 1. 生成 diff 供审查

在 worktree 内：

```bash
# 在 worktree 根目录
git diff develop...HEAD > /tmp/review.diff   # Unix
git diff develop...HEAD > $env:TEMP\review.diff  # Windows PowerShell
```

### 2. 启动独立审查（新会话 / 子 agent）

新开一个 agent 会话（或用当前会话的"假设你是审查者"提示），把 diff 文件和任务目标喂给它，要求只读审查：

```
请审查这个 diff。任务目标是：<从 NOTES.md 复制"目标"字段>。
请检查：
1. 改动是否完整实现了目标？
2. 有没有引入明显 bug、安全问题、或破坏项目红线（见下方红线清单）？
3. 测试是否覆盖了改动路径？
4. 有没有不必要的改动混入（顺手重构、无关格式化）？
只报告问题，不修改代码。每个问题给出严重级别（阻塞/建议/提示）。
```

### 3. 审查红线清单（审查者必查）

把以下项目红线贴给审查者，作为重点检查项：

- **端口**：有没有代码或测试监听 8687 / 8890？
- **路径**：有没有硬编码 `~/.modeldock`（应走 `src/util/paths.ts`）？
- **写盘**：有没有绕过 `atomicWrite()` 直接写文件？
- **SEA**：有没有引入 `import.meta.url`（应走 `process.execPath`）？
- **依赖**：`package.json` 有没有新增 native addon？
- **入口**：`src/cli.ts` 三路分发是否被改动？
- **文档**：用户可见行为变化是否同步了 CHANGELOG / README（见 `docs-sync.md`）？

### 4. 处理审查结果

| 级别 | 动作 |
|---|---|
| **阻塞** | 必须修复后重新审查（回到步骤 1） |
| **建议** | 与任务负责人确认后决定修或不修，不修要在 commit message 里说明理由 |
| **提示** | 记录即可，可不处理 |

### 5. 审查通过后才能 finish

```bash
node .agents/scripts/feature-branch.mjs finish <task-id>
```

## 实现者自查 ≠ 独立审查

- 实现者自己再检查一遍，**不能替代**独立审查——实现者对自己刚写的代码有盲区。
- 如果条件限制只能自查（如单人项目无第二个 agent），至少做到：隔一段时间再回头看 diff，假装自己是第一次看这段代码的人。

## 何时可以省略

- 纯文档改动（`.md` 文件、注释）且不影响行为——可自查后 finish。
- 机械性改动（重命名、格式化）且有测试兜底——可自查后 finish。
- 除此之外，**不要省**。

## 可直接复制的审查 Prompt 模板

把下面这段完整复制给审查 agent（新会话或子 agent），替换尖括号内容：

```
请审查这个 diff。任务目标是：<从 NOTES.md 复制"目标"字段，如"修复 presets 合并时用户配置被覆盖的问题">。

审查纪律：先读仓库根 REVIEW.md（各区域「失败长什么样」/红线/报告纪律——每条发现给文件+行号，风格/清理类不报，非本 PR 引入标 [存量]）。

项目背景：
- TypeScript ESM 项目，Node.js ≥22，全部纯 JS 依赖（无 native addon）
- 本地模型配置托管中心 + API 网关
- 数据模型：provider（上游凭据）→ profile（路由）→ harness（客户端接入方式）

请检查以下 4 个维度：

1. **目标完整性**：改动是否完整实现了任务目标？有没有遗漏的场景？
2. **明显问题**：有没有引入 bug、安全问题、或破坏项目红线？
3. **测试覆盖**：测试是否覆盖了改动的代码路径？有没有该写测试但没写的地方？
4. **改动纯度**：有没有不必要的改动混入（顺手重构、无关格式化、scope creep）？

项目红线（重点检查）：
- 端口：代码或测试不能监听 8687 / 8890（8687 是生产端口，8890 是用户 dev 实例）
- 路径：不能硬编码 ~/.modeldock，必须走 src/util/paths.ts
- 写盘：不能绕过 atomicWrite() 直接写文件
- SEA：不能用 import.meta.url（必须走 process.execPath）
- 依赖：package.json 不能新增 native addon
- 入口：src/cli.ts 三路分发（--sea-gateway / GUI / CLI）不能被破坏
- 文档：用户可见行为变化必须同步 CHANGELOG / README

只报告问题，不修改代码。每个问题给出严重级别：
- 🔴 阻塞：必须修复才能合并
- 🟡 建议：建议修复，但不阻塞
- 🔵 提示：记录即可，可不处理

diff 文件：<贴上 diff 内容或文件路径>
```

## 审查结果示例

假设任务目标是"新增 `modeldock export` 命令导出配置"，审查者可能返回：

```markdown
## 审查结果

### 🔴 阻塞（1 个）

1. **导出的 JSON 文件没有脱敏 API Key**
   - 位置：`src/cli/export.ts` 第 42 行
   - 问题：`export` 直接把 `secrets.json` 内容原样导出，包含明文 API Key
   - 建议：导出时用 `***` 替换 key 字段，或提供 `--include-secrets` 显式选项

### 🟡 建议（2 个）

1. **缺少测试覆盖错误路径**
   - 位置：`test/cli/export.test.ts`
   - 问题：只测了成功导出，没测"配置文件不存在"、"导出路径无权限"等错误场景
   - 建议：补充 2-3 个错误路径测试

2. **CHANGELOG 条目可以更用户化**
   - 位置：`CHANGELOG.md` 第 5 行
   - 问题：写的是"实现 export 功能"，不够用户视角
   - 建议：改为"**导出配置**：新增 `modeldock export` 命令，可导出当前配置为 JSON 文件"

### 🔵 提示（1 个）

1. **导出的 JSON 可以考虑 pretty print**
   - 当前是一行 JSON，建议加缩进方便阅读（不阻塞）

## 总结

发现 1 个阻塞问题（API Key 泄漏），必须修复后才能合并。建议处理 2 个建议项。
```

实现者根据审查结果修复阻塞问题后，重新生成 diff 让审查者复查，通过后执行 `finish`。
