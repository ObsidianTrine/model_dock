## 1. 现状架构（截至 2026-10-03 develop）

- **内核**：`src/util/i18n.ts` 的 `t(中文, English, params?)` **内联双语对**——中文原文即 key，两参必填（TS 结构性防漏翻），`{name}` 占位插值；`bi()/biCat()/biJoin()` 同时渲染两种语言，供审计条目双语存储。
- **语言解析链**：`--lang > 环境变量 MODELRDOCK_LANG > config.toml language > 默认 zh`（`src/config/lang.ts`，commander 分支必须在 `buildProgram()` 前 `initLang()`）。
- **请求级语言**：网关按 `x-modeldock-lang` 请求头把整个请求包进 `runWithLang()`（AsyncLocalStorage 随异步链传播、并发隔离），服务端请求期生成的文案（报错、卡片描述、审计摘要）跟随浏览器界面语言。
- **持久化条目**：审计日志 `op/target/detail/err` 双语双存（主字段恒中文渲染，`*_en` 缺省回退），控制台日志表按界面语言取字段。
- **Web 控制台**：`ui.ts` 内嵌 `data-i18n="中文||English"` 属性 + 浏览器端 `t(zh, en)`，与 `localStorage.mdk_lang` 联动，独立于服务端机制。
- **展示型数据字段**（预设 label/vendor、模型 display_name、adapter label）：一律 **getter 懒求值**调 t()，禁止模块加载期求值（会在 initLang 前固化语言）。
- **规模**：约 600 条 t() 调用 + ui.ts 约 450 条 data-i18n/t()；中文输出为逐字节契约（测试断言锚定）。

## 2. 【决策】维持内联双语对，暂不做字典化改造

2026-10-04 与用户评审结论：**"代码只写英文 + 中文进字典、展示时查表"** 的方案（gettext/i18next 形态）虽是业界标准，但本项目**暂不采用**。理由：

1. **源语言倒置**：本产品中文是第一语言——文案打磨约定（`.agents/conventions/docs-writing.md`）、测试逐字节断言、CHANGELOG 全部锚定中文，英文是第二语言。英文做源等于把最重要的语言降级为查表目标，改中文措辞要离开调用点去字典文件里找。
2. **防漏翻保障丢失**：现有 TS 双参是结构性约束（不写英文编译不过）；字典方案没有等价机制，漏一条翻译=中文用户看到英文回退，必须长期配 CI key 对齐脚本弥补。
3. **msgid 漂移陷阱**：英文原文一改，字典里对应中文条目静默失联（gettext 经典问题），翻译悄悄退回英文；内联对两语言永远并排可见，不存在此类漂移。

**代价（知情接受）**：加第三语言时需要一次性机械化迁移（见 §3），调用点双份文案略冗长。

## 3. 后续计划：第三语言的触发条件与迁移路径

### 3.1 触发条件（满足其一再启动）

- 出现**真实的第三语言需求**（可服务的用户群/合作方），而非"将来可能"。
- 引入**外部译者或翻译平台**（字典形态才能交给非程序员协作）。
- 单语言文案量增长到内联对明显影响代码可读性（当前规模不构成）。

### 3.2 迁移路径（机械化，预估一天内纯机械工作 + 全量回归）

1. **抽取**：复用 i18n 收尾轮的 TS AST 扫描器（未入库，按 `modeldock-project` 记忆中的方法重建）改造为抽取器——解析全部 `t(zh, en, params)` 调用，生成语义 key 目录（`src/i18n/zh.ts` + `en.ts` + `<l3>.ts`，key 用英文原义或哈希），同步覆盖 ui.ts 的 `data-i18n="zh||en"` 属性对。
2. **重写调用点**：codemod 把 `t(zh, en)` 改写为 `t('key', params)`；`bi()` 家族改为查目录双渲。
3. **回退语义取舍**（迁移时需用户拍板）：保留 zh 为缺省回退语言，或改为"key 缺失回落英文"的常规语义——建议前者（中文用户永不见英文碎片）。
4. **CI 门**：新增 key 集合一致性检查脚本（各语言目录 key 全等），进 test workflow。
5. **审计条目**：`bi()` 双语存储可维持（新增语言按需扩展字段），或改存 key+params 由展示端渲染。
6. **验证**：全量 npm test（中文断言不变）+ 隔离实例三语言往返实测。

### 3.3 不随迁移变化的约定

- 新增用户可见文案一律走 `t()` 双语（规范见 `AGENTS.md`「工程硬性约定·双语文案」）；无论未来是否字典化，这条约定都成立。
- 语言解析链、请求级 ALS、getter 懒求值、审计双语存储等上层机制与文案组织方式解耦，迁移不涉及。
