# 转发热路径基准（bench-baseline）

> ⚠️ **基线仅本机参考，不作 CI 门禁**——不同机器、不同负载下的数字不可直接比较；它只用于**同一台机器**上的 before/after 对比（改 relay 相关代码前跑一次、改后跑一次）。

## 复跑命令

```
node scripts/bench-relay.mjs          # 默认模式：30/30/20/100 样本，全程 <5min（实际 ~1min）
node scripts/bench-relay.mjs --quick  # 快跑模式：10/10/8/40 样本，全程 <2min
```

脚本自动完成：临时沙箱（`MODELRDOCK_FAKE_HOME`，系统临时目录）+ 18910-18919 白名单端口拉起 mock 上游与网关 → 四场景压测 → 统计输出 → 杀进程树 / 删沙箱 / 核实端口释放。全程黑盒压测，不改动 `src/**`。脚本末尾会打印一个「## 汇总」段落（含 CPU/Node/日期与数字表），把其中表格贴进下方「基线数字」即可。

## 场景定义

四个场景都经真实 harness token 鉴权（`config.toml [harness.bench]`），走 `POST /v1/messages`，单连接 keep-alive 串行请求，预热请求不计样本：

1. **大请求体 default_model 改写（5MB）**：请求体不带 `model` 字段 → 网关注入 profile 的 `default_model`（`JSON.parse` + 整包重序列化）——模型改写路径的完整开销。
2. **大请求体纯透传快路径（5MB）**：`model` 已是目标模型且在首键 → 浅扫描即止，不 parse 不重序列化——快路径开销。
3. **SSE 流式转发（≥1MB）**：mock 上游 128 × 8KB 块（~1ms/块）分块推流，测端到端吞吐（MB/s）与首字节延迟。
4. **小请求基准（1KB）**：鉴权 + 转发的最小开销下限。

> 场景 2 的「快路径」由 `src/gateway/relay.ts` 的 `rewriteModel` 逻辑保证（`final === wire` 时原 Buffer 透传）；黑盒视角只能验证「模型名未被改动」，是否发生重序列化不可从外部观测，因此该场景的数字对比要结合代码路径一起读。

## 基线数字（2026-10-29）

> 2026-10-29 默认模式实跑录入（--quick 冒烟先过，exit 0、端口零残留）。

| 场景 | n | mean(ms) | p50(ms) | p95(ms) | p99(ms) | rps | 首字节 p50(ms) | 吞吐 p50(MB/s) |
|---|---|---|---|---|---|---|---|---|
| 大请求体 default_model 改写（5MB） | 30 | 102.5 | 94.4 | 112.8 | 376.3 | 9.7 | - | - |
| 大请求体纯透传快路径（5MB） | 30 | 72.0 | 73.3 | 82.6 | 86.8 | 13.9 | - | - |
| SSE 流式转发（≥1MB） | 20 | 1306.3 | 1319.0 | 1392.3 | 1413.1 | 0.8 | 14.8 | 0.8 |
| 小请求基准（1KB） | 100 | 1.4 | 1.3 | 2.1 | 3.0 | 684.5 | - | - |

> **本次基线的负载背景**：录数时本机同时在跑 4 小时长稳压测（4 路混合流量 + 30s 采样，另一对端口），CPU 有约一成占用；p99 的 376ms 尖峰大概率来自同机负载。做 relay 改动的 before/after 对比前，建议空载重跑一次本表更新基线。

## 怎么读数字

- **mean/p50**：稳态开销；**p95/p99**：热路径抖动（GC、写日志、事件循环抢占）。优化改动的目标通常是「p95/p99 向 p50 收敛」而不是只降 mean。
- **场景 1 vs 场景 2**：两者只差「是否全量 parse + 重序列化」，差值即模型改写路径的 CPU 开销。
- **场景 3 首字节**：网关写响应头到首个数据块到达客户端的时间；**吞吐**：流式转发的字节速率上限。
- **场景 4 rps**：网关转发的最小请求处理速率，是其余场景的「开销下限」参照。
